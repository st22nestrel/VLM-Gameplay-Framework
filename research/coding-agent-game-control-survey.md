# Coding-agent game-control survey

Research date: 18 October 2026. 98 projects/interfaces are catalogued below, including adjacent tools explicitly marked as such. Separate implementations and meaningful forks are separate entries; this is not a count of independent game engines or proven working installations.

## Scope and evidence

The inclusion test is whether an existing coding-agent session can issue game decisions through a documented CLI, external MCP server, or explicitly identified shell-callable interface. A project that merely calls a model API internally does not qualify on that basis. Engine integrations and agent-native games are labelled because they solve different problems from controlling an existing Windows game.

- **D**: primary documentation names a coding agent/client, such as Claude Code, Codex, Cursor, Cline, Copilot, or opencode, and describes an integration or usable interface. This is documentation evidence, not a claim that I ran that client.
- **M**: an external MCP tool surface and transport are documented, so use from a coding agent that supports that transport is an interoperability inference. I did not runtime-test the connection.
- **C**: a shell/CLI interface is exposed to the coding agent.

I searched public repositories and project documentation, fetched 96 repository READMEs plus additional tool/configuration documents, and checked control capabilities rather than counting game-data search servers. No third-party project was installed or run. README claims are reported as maintainer claims, not independently reproduced benchmarks. This broad survey cannot guarantee every public project has been found.

Most relevant to this repository: **gameprobe**, **local-game-MCP**, **computer-use-for-all-agents**, **AutoControl**, **Orak**, and **ai-assisted-speedruns**. For timing and image-result design, also inspect **portal-agent**, **mcp-bizhawk**, and **mesen-for-ai**.

The downloaded evidence is under ignored `outputs/game-control-research/`; the public source links below are the durable references. No source code or configuration was changed for this research.

## What this means for our framework

1. **Compare gameprobe and local-game-MCP before building our MCP wrapper.** Both cover the closest problem: an external coding agent observing and controlling an existing game. Native suspension in gameprobe and calibrated profile actions/OCR waits in local-game-MCP are the main differences to investigate.
2. **Separate transport from gameplay intelligence.** Orak and Evalatro demonstrate exposing game tools independently of an internal model runner. Our existing synchronous GameSession already fits that separation.
3. **Keep a compact tool surface.** portal-agent and ai-assisted-speedruns use documentation/screenshot/exec; sts2-compact-mcp uses observe/act/inspect. These are useful alternatives to exposing every key or every game-specific operation as a separate tool.
4. **Make timing explicit.** Engine/emulator projects can pause or advance exact frames. A generic Windows input wrapper cannot assume those guarantees; it needs either bounded wall-clock steps, a validated pause mechanism, or a game-specific adapter.
5. **Keep our existing capture/input implementation unless comparison testing demonstrates a benefit.** The five-step Chess Titans run proves our current CLI path works on this machine; this survey does not establish that another project is a drop-in replacement for our game's capture, replay, focus, or input behavior.
